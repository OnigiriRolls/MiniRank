MiniRank — Process Document

A simulated keyword position tracker built with PHP (no framework), SQLite via PDO, and a simple MVC-ish structure.

Plan

Overall approach

I first started with understanding the requirements and deciding on the tech stack. Before implementing anything, I used OpenCode to help design the project structure. I implemented the required tasks first and then moved on to the stretch tasks. I generally followed this workflow:
  • Understand requirement
  • Make important design decisions
  • Create/review implementation plan
  • Implement a small increment with OpenCode
  • Review generated code and diff
  • Run/test the application
  • Manually modify/refactor if necessary
  • Fix bugs if necessary
  • Continue with the next increment
Throughout the implementation, I kept my own notes containing: tasks & ideas to implement/check, problems encountered with the AI agent, design decisions and a list of OpenCode sessions.

Milestones Order

M1 (+ UI list), M2, M3, M4, M5, M7, M8, M6, S1, S4, S5, S6, S2, S3
I chose the order based on required effort & complexity. M6 was considered throughout implementation, but I performed the dedicated security review after the core functionality was complete.

Design choices

  • Client-side vs server-side keyword search
    I considered whether the keyword search should happen on the server or in the browser. Because MiniRank is a small application and the keyword list is already loaded on the page, I chose the simpler client-side filtering approach.
  • Database IDs in the frontend
    The frontend uses database IDs (e.g. identify keywords). I intentionally accepted this for MiniRank because the application is small and the data is generated locally. However, I would make a different decision in a production application. I would avoid allowing database implementation details to leak unnecessarily through the application layers. I would introduce public identifiers/DTOs or another abstraction depending on the architecture.
  • Refresh / trend
    I decided that the refresh action should update both the keyword position and the trend. As a user of the app, I would expect the trend to be refreshed whenever the current position is refreshed.
  • CSV delimiter
    I tested the CSV download and found that Excel did not correctly split the values into columns when using ',' as the delimiter. I decided to use ';' instead, since this allowed the exported CSV to open correctly in Excel with the values separated into columns.

Tech choices

  • Plain PHP, SQLite, HTML/CSS/JavaScript, Composer / PHPUnit
    I chose this stack because it is lightweight, easy to set up, and appropriate for the size and scope of the project. A framework would have introduced additional configuration that was not necessary for this assessment. Since I had not worked with PHP before, this also gave me an opportunity to work with the language directly.
  • Chart.js for the chart stretch task
    In this case, I had to choose between Chart.js and ApexCharts. I wanted to use a simple, lightweight and well-established library for this small project. ApexCharts offers complex charts with many configuration options so I chose the simpler Chart.js.
  • Prettier & PHP Intelephense
    I chose popular & trusted formatters to keep the code consistently formatted and easier to read.

What I would change in hindsight

In hindsight, I would spend a little more time to think about arhitecture decisions. For example, I would decide in the beginning if I wanted to use a UI library like bootstrap. Another thing which I should have considered is how the routes/urls would look like. I use query params instead of clean urls ('project/id/keywords'). Since this application is small, I could have changed these decisions, but I didn't consider it was worth it.

Prompts & fixes

I only used the free model: DeepSeek V4 Flash. I first created a step-by-step plan with the AI and took design decision/implementation decisions. Only then I instructed the AI to implement, one step at a time. This way, I didn't consume a lot of quota.

Prompt 1

Prompt

I need to make an application called MiniRank, which is a keyword position tracker. All ranking data is simulated — no real search engines involved. I need to implement all these requirements:
  • M1 Keywords CRUD: add/edit/delete the keywords (search phrases) tracked for one configured website. Single-user app — no login.
  • M2 Seeded history: a seed script creates demo keywords with ~30 days of daily positions (1–100).
  • M3 Refresh simulation: a "Refresh positions" button generates today's positions server-side and updates the page via AJAX, without a full page reload.
  • M4 Keyword list: every keyword with its current position, a 7-day trend indicator (improved / declined / stable), and a text search.
  • M5 Keyword detail: a page per keyword showing the position history as a table.
  • M6 Security basics: parameterized queries (no SQL built by string concatenation), escaped output, and no secrets committed to the repository.
  • M7 Runs in 5 minutes: README with setup steps, a seed command, and a one-command start (php -S ... or docker compose up). Database: SQLite (recommended — easiest for us to run) or MySQL.
  • M8 Responsive: usable at phone width. Functional beats beautiful — we are not grading pixel-perfection.
I will use plain php, html/css/js and SQLite. Plan how the project structure should be: what folders do I need, how do I separate php code from frontend and database.

What happened

This was the first prompt when I started the app. It is important because it helped me create a good project structure, on layers: Model, View, Controller. This helped me separate concerns and navigate the project more easily. In addition, by mentioning the tasks that I needed to implement, the AI gave me a rough implementation plan. The agent considered security basics (M6) when planning and implementing right from the start.

Mistakes the AI made & how I caught them

  • Add/edit keyword form
    • The agent created the keyword page with a table, an input and a button for adding a new keyword. The agent created an edit form for editing. In this form, the agent added labels and actions for the add action as well, even though the add action was done using an input & button. I found this while looking through the code of the edit form. I deleted the labels & actions for add.
  • Test assert
    • When the agent implemented a test case for the trend function: testHistoryTooShortReturnsNull, it added an assert for Position::create. This is not correct since the test should only fail because of the trend function. I found this while checking the code. I deleted the incorrect assert.
  • Login & Register buttons duplication
    • On the Login page, the agent added buttons for login & register in the navbar (header) and in the body of the page as well. The buttons did the same actions. I found this while testing the application manually. I deleted the buttons from the page body.
  • Testing
    • The agent tried to test the implementation itself waisting quota, even though I didn't ask it to do this. I found this by looking in the agent chat. I added in my prompts: 'Don't test anything. I will test manually'.
  • Duplicated code
    • After the seeding script and trend calculation was implemented, I found that both used the same logic to simulate positions. The agent didn't detect the code duplication, so I instructed it to create a general function for simulating the keyword position, so it could be used in both places. I found this while checking the code.

Retrospective

What went well

The AI agent significantly accelerated implementation, especially for parts of PHP that I was less familiar with. The workflow I used was very useful and easy: plan -> implement -> check. I learnt that planning actually makes a difference, especially when you are limited by quotas. It really helped me to have a working UI early, so I could better verify the behaviour of the app and identify problems.

What I would do differently

If I repeated the assessment, I would spend more time during the initial planning stage identifying the dependencies between requirements. I would also be more explicit in prompts about the exact scope of a change and which files/areas should remain untouched. I would also be more clear in my prompts about what I wanted: an explanation, a plan, or code.
